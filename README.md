# common-harness

Claude가 결과물을 만들기 전에 목표를 확인하고, 내보내기 전에 스스로 검증하게 하는 스킬입니다. 보고서, 기획안, 메일, 분석, 코드처럼 정확도와 일관성이 중요한 작업에 씁니다.

## 무엇이 달라지나요

| 스킬 없이 | 스킬을 쓰면 |
|---|---|
| 모호한 요청에도 바로 쓰기 시작합니다 | 결과를 바꾸는 것만 먼저 묻습니다 |
| 수치와 날짜를 받은 그대로 옮깁니다 | 다시 계산하고, 맞지 않으면 짚어서 묻습니다 |
| 대화가 길어지면 앞에서 지적한 내용을 잊습니다 | 지시, 확인한 수치, 실수를 기록해 두고 다음 작업에 씁니다 |
| 확인하지 못한 내용도 사실처럼 씁니다 | "미검증"으로 표시하거나 알립니다 |

## 설치

**Claude 앱 (웹, 데스크톱)**

1. 이 저장소를 내려받아 `common-harness` 폴더를 ZIP 파일로 묶습니다. ZIP 안에 `common-harness/SKILL.md`가 들어 있어야 합니다.
2. Claude에서 **사용자 정의 > 스킬**로 이동합니다.
3. "+" 버튼을 누르고 "+ 스킬 만들기"를 누른 뒤 "스킬 업로드"를 고릅니다.
4. ZIP 파일을 올립니다. 스킬 목록에 `common-harness`가 보이면 켜 둡니다.

스킬을 쓰려면 설정에서 코드 실행 및 파일 생성 기능이 켜져 있어야 합니다. 메뉴 이름은 바뀔 수 있으니, 다르게 보이면 [Claude에서 스킬 사용하기](https://support.claude.com/ko/articles/12512180) 문서를 확인하세요.

**Claude Code**

이 저장소의 `common-harness/SKILL.md`를 프로젝트의 `.claude/skills/common-harness/SKILL.md` 위치에 둡니다.

## 빠른 시작

요청 앞에 `/common-harness`를 붙이거나, 요청에 아래 말 중 하나를 넣습니다.

| 호출 방법 | 예시 |
|---|---|
| `/common-harness` | `/common-harness 다음 분기 마케팅 계획서 써줘` |
| "검증해서", "정확하게", "꼼꼼하게", "하네스로" | `3분기 실적 요약을 검증해서 써줘` |
| "인터뷰해줘" | `블로그 글 쓰려는데 시작 전에 인터뷰해줘` |

확실하게 적용하려면 `/common-harness`로 부르세요. 말로 부르는 방식은 Claude가 그 말을 보고 스킬을 쓸지 판단합니다.

한 번 부르면 그 대화가 끝날 때까지 적용됩니다. 새 대화에서는 다시 불러야 합니다.

## 동작 순서

| 단계 | 하는 일 |
|---|---|
| 1. 목표 확인 | 누구를 위한 것인지, 왜 필요한지, 무엇이 성공인지, 가장 큰 제약이 무엇인지 확인합니다. 빠진 것이 있으면 묻습니다 |
| 2. 작성 | 핵심을 먼저 쓰고, 요청하지 않은 설명은 덧붙이지 않습니다 |
| 3. 검증 | 수치를 다시 계산하고 사실을 대조한 뒤, 다섯 기준(정확성, 논리성, 간결성, 실용성, 목표 달성도)으로 평가합니다 |
| 4. 수정 | 기준에 못 미친 부분만 고칩니다. 최대 두 번까지 고칩니다 |
| 5. 출력 | 통과하면 결과물만 보여 줍니다. 점수표는 붙이지 않습니다 |

짧은 질문이나 간단한 수정 같은 가벼운 요청에는 이 절차를 붙이지 않고 바로 답합니다.

## 질문은 이렇게 합니다

- **결과를 바꾸는 것만 묻습니다.** 답을 거의 틀림없이 맞힐 수 있는 것은 묻지 않고 가정으로 둡니다.
- **첫 질문은 묶어서 합니다.** 서로 답에 영향을 주지 않는 질문을 한 번에 보냅니다.
- **질문마다 추측을 붙입니다.** 추측이 맞으면 "맞아"라고만 답하면 됩니다.
- **필요할 때만 이어서 묻습니다.** 추측이 빗나갔거나 답이 흐릿할 때 그 부분만 하나씩 묻습니다.
- **정리되지 않으면 물러섭니다.** 여러 번 물어도 정해지지 않으면 작은 초안을 먼저 볼지, 목표부터 다시 이야기할지 고르게 합니다.

```
쓰기 전에 두 가지를 확인하겠습니다. 추측이 맞으면 "맞아"라고만 하셔도 됩니다.
1. 누가 읽나요? 팀장님께 올리는 주간 보고로 짐작합니다.
2. 무엇에 관한 보고인가요? 지난주 업무 결과로 짐작합니다.
```

**가벼운 요청에도 묻는 경우가 세 가지 있습니다.**

| 경우 | 동작 |
|---|---|
| 해석이 갈릴 때 | 묻지 않고, 고른 해석을 "가정:" 한 줄로 밝힙니다 |
| 틀리면 비용이 클 때 (돈, 계약, 법, 세금, 건강, 안전) | 답을 바꾸는 조건을 묻습니다 |
| 요청에 모순이나 오류가 있을 때 | 어긋난 부분을 짚고, 무엇을 원하는지 묻습니다 |

**질문을 받고 싶지 않다면** "묻지 말고 해줘", "알아서 해줘", "빨리"라고 하세요. 가정을 세워 진행하고, 그 가정을 결과물 첫머리에 밝힙니다.

**예약 실행처럼 답할 사람이 없는 환경**에서는 질문으로 멈추지 않습니다. 가정을 밝히고 진행하며, 진행할 수 없는 부분은 "막힌 점"으로 보고합니다.

## 답변에 붙는 표시

| 표시 | 뜻 | 할 일 |
|---|---|---|
| `가정: ...` | 정해 주지 않은 것을 이렇게 가정했습니다 | 틀렸으면 한마디로 바로잡으세요 |
| `기준 변경: ...` | 앞 작업과 기준이 달라졌습니다 | 의도와 다르면 알려 주세요 |
| `보완 가능: ...` | 자료를 더 주면 나아질 부분입니다 | 필요하면 자료를 주세요 |
| `미검증` | 확인하지 못한 내용입니다 | 쓰기 전에 직접 확인하세요 |
| `검증: ... (미달)` | 두 번 고쳐도 기준에 못 미쳤습니다 | 적힌 원인과 제안을 보세요 |
| `막힌 점: ...` | 이 정보가 없어 진행하지 못했습니다 | 해당 정보를 주세요 |
| `정리: ... 이대로 작성할까요?` | 이해한 의도를 확인받는 중입니다 | "네" 또는 고칠 점을 답하세요 |

## 명령어

메시지를 `-harness` 또는 `-하네스`로 시작하면 명령으로 봅니다.

| 명령 | 동작 |
|---|---|
| `-harness off` 또는 `-하네스 꺼줘` | 이후 요청에 절차를 적용하지 않습니다 |
| `-harness skip` 또는 `-하네스 이번만 꺼줘` | 같은 메시지에 이어지는 요청 하나에만 적용하지 않습니다 |
| `-harness status` 또는 `-하네스 상태` | 켜져 있는지 꺼져 있는지 알려 줍니다 |

다시 켜려면 `/common-harness`로 스킬을 다시 부릅니다. 꺼 둔 동안에도 "검증해서"를 붙인 요청에는 그 요청 하나에만 적용됩니다.

## 작업 기록

스킬은 대화 안에서 아래 여섯 가지를 기록해 두고 다음 작업에 씁니다. 평소에는 보이지 않습니다.

| 기록 | 담는 내용 |
|---|---|
| 동작 규칙 | 계속 지키라고 한 지시 (호칭, 표기 방식 등) |
| 평가 규칙 | 결과물별 성공 기준 |
| 참고 자료 | 받은 자료와 찾은 자료 중 아직 확인하지 않은 것 |
| 신뢰 정보 | 확인을 마친 사실과 수치 |
| 실수 기록 | 틀린 것, 원인, 다음에 지킬 것 |
| 출력 | 내보낸 결과물의 최종본 |

- **보기:** "실수 기록 보여줘", "기록 전부 보여줘"라고 하면 요청한 항목만 보여 줍니다.
- **고치기와 지우기:** "기록에서 예산 내용은 지워줘"처럼 말하면 그대로 합니다.
- **정리:** 기록이 60줄을 넘거나 결과물이 5개를 넘으면 정리할지 묻습니다. "정리", "새 대화용 요약", "그대로" 중에서 고릅니다.
- **범위:** 기록은 그 대화 안에서만 유지됩니다. 새 대화로 이어 가려면 "새 대화용 요약"을 받아 붙여 넣으세요.

파일을 쓸 수 있는 환경에서는 작업 폴더의 `.common-harness/`에 저장합니다. 파일을 쓸 수 없는 환경에서는 대화 내용을 기록으로 삼습니다.

## 사용 예

**모호한 요청**

```
사용자: /common-harness 보고서 좀 써줘
Claude: 쓰기 전에 두 가지를 확인하겠습니다. 추측이 맞으면 "맞아"라고만 하셔도 됩니다.
        1. 무엇에 관한 보고서인가요? 최근 업무 결과를 정리하는 보고서로 짐작합니다.
        2. 누가 읽나요? 팀장님께 올리는 보고로 짐작합니다.
사용자: 둘 다 맞아. 지난주 고객 문의 현황이고 총 132건, 배송 58건, 환불 41건, 기타 33건이야.
Claude: 가정: 한 장 이내 보고로 썼고, 집계 기간은 11월 16일(월)~22일(일)로 적었습니다.
        (보고서 본문)
```

**수치가 맞지 않는 요청**

```
사용자: /common-harness 회의가 12월 15일(월)인데 오늘부터 며칠 남았어?
Claude: 날짜와 요일이 서로 맞지 않습니다. 2026년 12월 15일은 화요일이고, 그 주 월요일은 12월 14일입니다.
        회의가 12월 14일(월)인가요, 12월 15일(화)인가요?
```

## 비용

스킬을 쓰면 토큰이 더 듭니다. 아래는 시험 환경에서 잰 값을 바탕으로 한 추정입니다.

| 상황 | 스킬 없이 쓸 때와 비교 |
|---|---|
| 가벼운 요청에 바로 답할 때 | 답변 한 번에 약 1.1만 토큰 추가 (스킬 문서를 읽는 비용) |
| 무거운 요청을 질문 없이 작성할 때 | 답변 한 번에 약 1.5만~1.7만 토큰 추가 |
| 질문이 오갈 때 | 오간 횟수만큼 답변이 추가됨 |

비용을 줄이려면:

- 검증이 필요 없는 작업은 스킬을 부르지 않은 새 대화에서 합니다.
- 한 번만 건너뛰려면 `-harness skip`을 씁니다.
- `-harness off`는 질문, 검증, 기록에 드는 비용만 줄입니다. 스킬 문서를 읽는 비용은 그 대화가 끝날 때까지 남습니다.

## 시험 결과

Claude를 대상으로 한 시뮬레이션 결과입니다. 표본이 작고, 일부는 이전 버전으로 시험했습니다.

| 시험 | 결과 |
|---|---|
| 요청 50개를 스킬 사용과 미사용으로 비교 (초기 버전) | 조건을 지킨 답변: 사용 50건, 미사용 48건. 모호한 요청 12건에 먼저 질문: 사용 12건, 미사용 10건 |
| 모호한 요청 6개를 5번씩 반복 (초기 버전) | 먼저 질문: 사용 30회 중 30회, 미사용 30회 중 20회 |
| 최종 결과물 12쌍을 가리고 채점 (5점 만점, 이전 버전) | 사용 4.82점, 미사용 4.62점 |
| 여러 유형의 요청 31회 (작업 기록, 끄기 명령, 기록 정리) | 28회 통과, 3회 부분 통과, 실패 없음 |
| 질문 규칙 29회 (묶어서 묻기, 추측 붙이기, 물러서기) | 미리 정한 제약 조건에 걸린 경우 없음 |

## 알려진 한계

- 확인하지 못한 수치를 처음에는 알리지만, 같은 대화의 다음 결과물에서는 알림 없이 쓰는 경우가 있었습니다.
- 작업 기록은 새 대화로 자동으로 넘어가지 않습니다.
- 파일을 쓸 수 없는 환경에서의 동작은 한 번만 확인했습니다.
- `-harness` 명령은 스킬을 부른 대화 안에서만 알아듣습니다.
- 답을 계속 피하는 경우, 물러서기를 제안하기 전에 질문을 한 번 더 할 수 있습니다.
